# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Jake Motta's personal website (jakemotta.com): a playful showcase of his work, music and other projects. The product goals that shape most changes:

- **Background music with an in-sync visualizer.** Music keeps playing while the visitor moves around the site, and the visualizer reacts to the audio that is actually playing, not to a timer.
- **Project previews.** Projects are linked from the site, and each one should show a good preview (image, title, date, description) before the visitor clicks through.
- **Fun over corporate.** The look is deliberately loud: a hue that cycles continuously, particle backgrounds, cheeky copy.

## Commands

Yarn is the package manager (`yarn.lock`, and CI runs `yarn install --frozen-lockfile`).

```bash
yarn dev          # CRA dev server on http://localhost:3000 (also the "dev" config in .claude/launch.json, which runs it muted)
yarn build        # production build into build/, then scripts/prune-build.mjs strips what must not be published and scripts/write-sitemap.mjs writes build/sitemap.xml
yarn projects:convert   # regenerate the static .html pages of the PHP project sites (see Project previews)
yarn projects:screenshot [id…]   # retake the project card images from the running previews; needs `yarn dev`
yarn projects:greenfoot [id…]   # compile the Greenfoot games in scripts/build-greenfoot.mjs's GAMES to JavaScript; needs a JDK (Jake's is in ~/.jdks/)
yarn projects:greenfoot-pack <scenario folder> <jar> [name]   # pack an unpacked .gfar into a jar the build can read
yarn projects:greenfoot-check <id>[,<id>…] [--keys …]   # smoke-test compiled Greenfoot games in headless Chrome; needs `yarn dev`
yarn projects:ambii [dashboard|player|mobile]   # rebuild the Ambii Business demo apps from demos/ambii/ into public/projects/ambii-business/; needs their source, which isn't committed
yarn test         # Jest in watch mode (react-scripts)
yarn test --watchAll=false src/path/to/File.test.tsx   # one test file, single run
yarn prettier     # format everything (2 spaces, single quotes, semicolons, printWidth 200)
yarn modpack:release <release-folder> [--force]       # publish a Minecraft modpack release, see below
yarn devlog:stats # refresh the dev log's Claude usage and commits (src/devlog/stats.json) from this machine; commit the result
```

There are no tests in `src/` yet, and no lint script beyond the ESLint that CRA runs during `dev`/`build`. Type errors surface through the CRA build.

## Architecture

Create React App (react-scripts 5) + TypeScript, React 19, react-router v7, Ant Design 5, Tailwind 3 alongside per-component SCSS, zustand for state.

**Layout of `src/components/`** follows atomic design: `atoms/` (small pieces: the music player, the transport and sliders, cover art, project images, the eq bars), `templates/` (page shells: the color-shifting background and the overlay), `pages/` (routes). Each folder has an `index.ts` barrel, and new components are exported through it.

**The board and its overlays** (full spec in [`docs/board.md`](docs/board.md)). The whole site is one bento board, `pages/home`, at `/` (and `/home`). Its tiles open as overlays drawn over it, each a route of its own: `/library` (`pages/music`), `/project` (all projects, `pages/project-gallery`), `/project/:id` (`pages/project`) and `/project/:id/:page` (a hub's page, one step in), `/minecraft` (`pages/minecraft`) and `/devlog` (`pages/devlog`, linked from the Hero). A tile that holds several things opens through an expand link in its header, like the Now Playing tile's Library. In `App.tsx` the board is a layout route and the overlays render into its `<Outlet />`, so the board stays mounted, dimmed and inert, behind whichever one is open, and Back, Escape or the close button return to it. Overlays use `templates/bento-overlay`, which portals them to `<body>`, and head themselves with `templates/overlay-header`: one shared header (Jake asked that they all match), whose first line holds the title level with the close button, anything that belongs beside it (the library's tabs), with a subtitle under it. A panel starts it 16px down so the title lines up with the button. Any other path redirects to `/`. An overlay's path must never match a folder in `public/` (`downloads`, `images`, `music`, `projects`, `vendor`): the server serves the folder instead of the app, so the library is at `/library`, not `/music`.

**What stays mounted across routes.** `App.tsx` renders the `<Routes>` and, beside them (outside `BrowserRouter`), `<TsParticleBackground />` and `<MusicPlayer />`. Because the player sits outside the routes it survives navigation, which is what lets music keep playing between pages. Anything else that must persist across pages belongs there too.

**Theme / color cycling.** `App.tsx` runs a `requestAnimationFrame` loop that rotates the hue through 360° every 30s from a random start, and whenever the whole-degree hue changes it calls `applyHue` (`contexts/ThemeContext.tsx`), which writes the four colors straight to the CSS variables `--color-primary`, `--color-primary-dark`, `--color-primary-light` and `--color-primary-ink`. The hue is never React state: re-rendering the app twelve times a second was the site's biggest cost ([`docs/performance.md`](docs/performance.md)). Tailwind's `primary`, `primary-dark`, `primary-light` and `primary-ink` colors (`tailwind.config.js`) point at those variables. So use `text-primary`, `bg-primary-dark` etc. (or the variables in SCSS) rather than fixed colors, and read the hue in a component through the variables, never through a context value. No antd components are in use, and the antd `ConfigProvider` was removed with the hue state; only antd's reset stylesheet is still loaded. One added later needs a `ConfigProvider` whose tokens follow the hue without re-rendering the app. `templates/color-shifting-background` paints the page background from `var(--color-primary)` and is the shell the board wraps itself in.

**Music and visualizer** (full spec in [`docs/music.md`](docs/music.md)).
- `store/audio.ts` (zustand) holds the playing `audioUrl`, the `shuffled` library (what plays next), a `history` for Previous, `isPlaying`, `volume` and the visitor's `entry` choice. It also holds the `<audio>` element and its `AudioContext`, which the player registers, so every control (`togglePlayback`, `playNext`, `playPrevious`, `setVolume`) drives the one element from anywhere. `setAudioUrl` plays a track now and takes it out of the shuffle. When a track ends, `playNext` plays the next shuffled one. There is no manual queue (removed on 2026-10-27). The shuffle is kept topped up, never repeating the track that just ended, so the library's "Up next" always has something to show; it lists the next ten (`upNextTracks()` in `common/music.ts`). The board's Up next tile became the Dev log tile on 2026-10-29.
- `atoms/music-player` owns the one `<audio>` element and has no buttons of its own. It builds the Web Audio graph once, on the first track: a media element can feed only one `MediaElementAudioSourceNode` for its lifetime. A rAF loop reads two adaptive bands (lows and highs) and writes the vignette's `box-shadow` straight onto `.audio-visualizer` through a ref. It also writes the levels to `audioLevels`, which the small `EqBars` read in their own loops. That direct DOM write, instead of React state, keeps the visualizers in sync at frame rate; keep per-frame work on that path (the seek slider follows the same rule). It also pauses when a framed preview from the same origin posts `{ type: 'jakemotta:media-playing' }`, so a project with its own sound doesn't play over the music.
- Browser autoplay rules: audio can only start after a user gesture. That's why the board's Now Playing tile asks the visitor to choose sound or silence before anything plays, and the rest of the board waits, dimmed, until they do. "Play with sound" starts on a random song from Jake's own, his recent listens or his playlist (`store/first-song.ts`, since 2026-10-29; [`docs/board.md`](docs/board.md#sound-or-silence)). `AudioContext.resume()` is called before `play()` for the same reason.
- **Claude's previews are silent.** The `dev` config in `.claude/launch.json` sets `REACT_APP_MUTE_AUDIO`, which loads `src/muteAudio.js` into the app (`index.tsx`) and into every static page under `public/` (`setupProxy.js` inlines it as it serves them). Media is muted and Web Audio renders to no device, but the visualizer still moves. Jake asked for this, so keep it on; a `yarn dev` run by hand stays loud. Details in [`docs/music.md`](docs/music.md#silent-while-claude-previews).
- **Songs from YouTube** share the shuffle and the controls, as Jake asked on 2026-10-27 ([`docs/music.md`](docs/music.md#songs-from-youtube)).
  - **Which tracks:** a track whose `url` is `youtube:<id>`, `spotify:<id>` or `song:<artist>/<title>` (`isStreamed()` in `common/music.ts`) plays in `atoms/youtube-player`, YouTube's embedded player, not the `<audio>`. The last two are matched through the listening Worker.
  - **Where they come from:** `youtubeSongs` in `constants.ts`, Jake's Spotify playlist (dealt into the shuffle when the Worker sends it) and play buttons on the Recent listens rows.
  - **Controls go through `media()`** in the store, never straight to `audioElement`, so they drive whichever player has the song.
  - **Ready ahead:** the player is made once the visitor is in and the browser is idle, kept invisible until a song's video starts, and always given the site's volume, since YouTube brings back a volume of its own when a video loads (2026-10-28).
  - **The video:** it shows where the cover would, over a `VideoSlot` (the player card's, or the floating player's when no card is in sight). It's never moved in the page, since moving an iframe reloads it; it's laid over the slot every frame instead.
  - **YouTube's rules apply,** as for listen-along: always visible, never under 200×200. The exception is the hidden tab: since 2026-10-28 these songs play on there, as Jake chose, knowing YouTube's policies forbid it ([`docs/music.md`](docs/music.md#songs-from-youtube)). The vignette rests through these songs.
- `realtime-bpm-analyzer` and `react-use-audio-player` are installed but not used yet.

**What Jake's listening to** (full spec in [`docs/listening.md`](docs/listening.md)). On the board as the "Recent listens" tile (`EarsTile`, in the cell that was "Surprise me"), whose Lately link opens the library on its Recent listens tab (`/library?tab=recent`). The separate `/listening` overlay was removed on 2026-10-27; that path now redirects to the tab.
- **Data:** `api/listenbrainz.ts` reads Jake's public ListenBrainz account (`LISTENBRAINZ_USER` in `common/listening.ts`) from the browser, with no key. `store/listening.ts` holds what it found and polls only while the page is visible. The pieces are `atoms/now-playing` (the card, `compact` on the board, and `useNowListening()`, which the overlay shares), `atoms/lately`, `atoms/listen-row` and `atoms/listen-cover`. They show and link out, and a song row that can play from YouTube has a play button too (see Songs from YouTube above).
- **Listen along:** `atoms/listen-along` plays the YouTube copy of what Jake has on Spotify, in sync, using YouTube's embedded player. It's mounted beside `<MusicPlayer />` in `App.tsx`, and its button stays hidden until the Worker answers, which it won't until it's deployed.
  - **Where the data comes from:** a Cloudflare Worker, `workers/listening` (`/api/listening/now`; `/playlist` and `/match` serve the site's own player). It holds the Spotify and YouTube keys, matches each track, and deploys with `wrangler`, not the FTP workflow. `/match` only looks up Jake's own songs (his playlist and ListenBrainz history), so nobody else can spend the YouTube search quota. `src/setupProxy.js` forwards the path to it under `yarn dev`, and `tsconfig.json` excludes `workers/`.
  - **YouTube's rules:** the player stays visible above everything, never under 200×200, and pauses when the tab is hidden.
  - **The visualizer:** an opt-in tab-audio capture (desktop Chrome and Edge) feeds the music player's analyser and never the speakers. That's why the player's source feeds the analyser beside the speakers rather than through it.
- **Sources:** only Spotify reaches ListenBrainz for now, through ListenBrainz's own link. Web Scrobbler (YouTube Music on the web) was skipped, and the iPhone sync, `scripts/ytmusic-sync` (Python, ytmusicapi), is shelved because ytmusicapi's sign-in no longer works. Past YouTube Music plays can still come in through `import_takeout.py`.

**Content data.** The music list (`musicList`) and the projects (`homeProjectList`) are static arrays in `common/constants.ts`; `common/music.ts` derives the shuffle library and looks tracks up by URL. Adding a song or project means editing that file and putting its assets in `public/` (`public/music/`, `public/images/music/`, `public/images/projects/`), referenced by absolute paths like `/music/foo.mp3`. A track's `description` shows in the library's player and under the song in its list, so leave it empty rather than writing filler. The library's Favorite artists aren't a list here any more: since 2026-10-28 they're Jake's most-listened artists, from Spotify's long-term top artists through the listening Worker, or ListenBrainz when it can't say ([`docs/music.md`](docs/music.md#playback-and-the-shuffle)).

## Style

Decisions Jake has made about the look. Follow them unless he says otherwise.

- **The color-cycling background and its UI stay.** The board sits on `ColorShiftingBackground`, the hue keeps cycling, even behind an overlay (the particles rest there, so framed projects get the browser's thread; see `docs/board.md`), and the particles and the inset vignette that pulses with the bass are part of the identity. New work goes on top of them; it doesn't replace or tone them down. The player lives in the board's Now Playing tile (`PlayerCard`, which the library shows too). Wherever that tile is out of sight (behind an overlay, and on phones once it scrolls away) one `FloatingPlayer` takes over: a circle of the cover, ringed with the song's progress, that opens into the controls on a click, which the visitor can drag to any corner or edge middle. It shows only while music plays. It replaced every per-overlay mini player on 2026-10-27.
- **All color comes from the cycling hue.** Use `primary` (`hsl(h, 40%, 60%)`) for the page ground and `primary-dark` (the same hue at lightness −30) for surfaces like tiles and panels, through the Tailwind classes or the CSS variables. Don't introduce fixed hex colors for UI; they stop matching as the hue moves. The `secondary` and `brand` colors in `tailwind.config.js` are unused leftovers.
- **Text on `primary-dark` surfaces uses `primary-light`, not `primary`.** `primary` on `primary-dark` is only about 3:1, which is fine for 24px bold titles but too faint for body text. `primary-light` (`--color-primary-light`, `hsl(h, 45%, 94%)`) is the pale tint for that text and for light buttons; keep `primary` for accents.
- **Text straight on the ground uses `primary-ink`.** `primary-dark` on `primary` is under 3:1 too. `primary-ink` (`--color-primary-ink`, `hsl(h, 45%, 15%)`) is the near-black of the hue, for text and rims on the page ground and on `primary-light` tiles.
- **Type:** the system font stack, bold weights: 900 for names and headings, 800 for most other text. Tiles head themselves with a small uppercase eyebrow or a bold heading; there are no sticky section titles any more.
- **Copy is in Jake's voice, never technical**, as Jake asked on 2026-10-27. Explanations on the site read like Jake talking about his own work ("Everything I've built, drawn and animated over the years"), in the first person, and never explain how the site works (no "runs as plain files in your browser", "through Ruffle", "from ListenBrainz", "the music keeps going"). The how belongs in `docs/`. Instructions a visitor needs to act on, like installing the modpack, stay plain and practical.
- **Tone is playful.** Small tilts, lifts and springy easing on hover are welcome; corporate polish is not the goal. Every tile leans its own way on hover (`--tilt`), and `prefers-reduced-motion` turns the tilts and spins off.

### The board

**Direction: the Bento board**, built from the "2 · Bento" pages of the [jakemotta.com Layout Concepts canvas](https://claude.ai/artifact/Ppw6uZbYxKSoktKAXB6b4U). Jake picked it over five other layouts. Tile by tile it's described in [`docs/board.md`](docs/board.md); the rules that hold across it:

- Desktop (1100px and up) is four columns by three rows, exactly one screen tall, with no page scroll. Tablets get two columns and phones one, and there the board scrolls.
- A tile that does one thing is one link or button; a tile that holds several things is a `<section>` with a heading.
- Opening a tile never leaves the board: it's an overlay route over it (see Architecture).
- Before the visitor chooses sound or silence, only the Now Playing tile is live; the rest are dimmed and inert. The choice isn't remembered across reloads, since sound can't start without a click anyway.

### Project tiles

Projects appear on the board as the featured tile (the first, newest entry in `homeProjectList`, marked "Newest") and as small screenshots in the Projects tile and the all-projects overlay. Every one of them must:

- be a real link (a router `<Link>` to `/project/<id>`), so keyboard focus and middle-click work and the music keeps playing, with a visible `:focus-visible` ring (pale with a dark halo, so it shows on any surface);
- show a preview through `atoms/project-image`: the project's screenshot from `public/images/projects/`, or, when there is none, a monogram tile in the hue. Never an empty `src` or a placeholder box;

## Branches and staging

Jake asked on 2026-10-27 for every task to go through its own branch into `staging`, so chats stop asking to commit and deploy and can't overwrite each other's work. `master` is what's live; `staging` is everything finished and waiting to go live.

- **One task, one branch, one worktree.** Before editing anything, move into a worktree of your own on a new branch cut from `staging`. A session the app started in a worktree already is one (run `git merge staging` first if it was cut from `master`). Otherwise, from the main checkout: `git worktree add .claude/worktrees/<name> -b claude/<name> staging`, then work only in that folder. Never edit in the main checkout (`C:\Users\Jake\Documents\Github\jakemotta`): other chats share it, and it stays on `master`. A worktree has no `node_modules`; run `yarn install --frozen-lockfile` there before `yarn dev` or `yarn build`.
- **Commit as you go, without asking.** Commits on the task branch are routine.
- **When the task is done, merge it into `staging`, without asking.** In the worktree, `git merge staging` (resolve any conflict there, keeping both sides' work), then `git push . HEAD:staging`. That only fast-forwards, so it refuses rather than lose anything that reached `staging` in the meantime; merge again and retry. Never check `staging` out anywhere, or it can't be moved this way. Then `git worktree remove` a worktree you created, and name the branch in the wrap-up.
- **Never deploy, and don't offer to.** Jake decides when: on his word, merge `staging` into `master` and push `master`. Don't push `staging` or task branches either unless he asks.

## Deployment

Pushing to `master` deploys (`.github/workflows/deploy.yml`), which happens only when Jake says so (see Branches and staging): `yarn build`, then `lftp mirror --reverse` of `build/` to the host over FTPS. Things that follow from how it works:

- **Nothing is ever deleted on the server** (no `--delete`), so the standalone `/projects/` sites and old hashed bundles survive every deploy. That also means a file once uploaded stays public, which is why `yarn build` prunes `pistol-art/myAdmin` (an old CMS admin whose `config.php` holds database credentials), the Ambii build in `pistol-art/files` and every `.php` under `projects/` before the upload ever sees them.
- **Files are compared by size only** (`--ignore-time`), because CI rewrites every timestamp. A file whose contents change but whose length doesn't would never be re-uploaded. Hashed bundles are safe; `index.html`, `asset-manifest.json`, `privacy.html`, `sitemap.xml`, the modpack pointer files, the Ambii Business demos' `index.html` pages and invoice page, Asteroids' `index.pck` and the Greenfoot games' `web/manifest.json` are uploaded unconditionally for this reason. Any new file that is rewritten in place under a fixed name needs the same explicit `put` in the workflow.
- **Only the project sites that changed are compared.** The upload's time went on lftp listing the server's folders, not on sending files, and `projects/` holds 700 of build's 720 folders. So the workflow finds the commit of the last successful deploy (through `gh run list`) and mirrors everything except `projects/`, then only the `projects/<site>/` folders that changed since that commit (since 2026-10-27; deploys had taken 5 to 11 minutes, 3 to 6 of them uploading). When it can't tell, it mirrors them all, as before. To force that, for example to put back a file removed from the server by hand, run the workflow from the Actions tab with "Mirror every project site" ticked.
- **No source maps are published**, as decided on 2026-10-27. `.env.production` (committed; build settings only, never secrets) sets `GENERATE_SOURCEMAP=false`. The source is public on GitHub, nothing reads the maps in production, and each build's maps would otherwise pile up on the server. To debug the live bundle, reproduce under `yarn dev`, or turn them on for one deploy. The 16 maps uploaded before this (`static/js/*.map`, `static/css/*.map`, about 76 MB) were moved to cPanel's Trash on 2026-10-27.
- **Cloudflare caches files for up to a week.** A card image retaken after it was deployed gets `?v=<n>` bumped on its `image` in `constants.ts`, so the cards ask for a fresh copy (asteroids, coloris, isguy, greenfoot-pokemon and personal-site are at `?v=2` since 2026-10-28). The site is served through Cloudflare, and static files go out with `Cache-Control: public, max-age=604800`. So a file rewritten under the same name, such as a card image retaken by `yarn projects:screenshot`, can stay stale at Cloudflare and in visitors' browsers for up to seven days after the deploy, although the server already has the new copy. After the 2026-10-28 deploy five card images were still the old shots at Cloudflare (the Greenfoot games with their Play button among them), out of 1,065 changed files. Purging the file's URL in Cloudflare (Caching → Configuration → Custom Purge) clears it there. To tell whether the server has a file, request it with a throwaway query string (`?v=1`), which Cloudflare fetches fresh.
- `FTP_SERVER` must not be a Cloudflare-proxied hostname (Cloudflare does not pass FTP); the workflow's preflight step checks for this. It is the Namecheap server's own name, `premium313.web-hosting.com`, whose certificate (`*.web-hosting.com`) passes the workflow's certificate check; a `jakemotta.com` name would not. `FTP_SERVER_DIR` is `/public_html/`, because the FTP accounts start in the home directory, one level above the web root.

Hosting is Namecheap shared hosting (cPanel user `jakedufc`), served by LiteSpeed, which reads Apache `.htaccess` files. `public/.htaccess` sends unknown paths to `index.html` so client-side routes such as `/home` survive a refresh, and it excludes `/projects/` so the standalone sites keep their own rewrite rules. It also turns folder listings off (`Options -Indexes`, since 2026-10-28): until then `/projects/`, `/images/`, `/music/` and `/downloads/` listed every file on the server. A new top-level route needs no server change; a new directory of static files that must bypass the SPA does.

**`public/privacy.html`** is a standalone page at `jakemotta.com/privacy.html`, outside the app. The "jakemotta" Google OAuth app behind the YouTube Music sync names it as its privacy policy, with `https://jakemotta.com` as its home page; Google requires both to keep the app published. So keep it at that path, and update it when the site or the sync starts handling visitors' data differently.
