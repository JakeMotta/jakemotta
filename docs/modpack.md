# Minecraft modpack downloads

`/minecraft` (`src/components/pages/minecraft`) is the download page for Progression Survival, the modpack for Jake's modded Minecraft server. It opens as an overlay on the board, from the modpack tile. The pack itself is made in its own repository, `minecraft-progression` (`Documents/Github/minecraft-progression`, private on GitHub as `JakeMotta/minecraft-progression`), and only its finished releases are published here. Since 2026-10-30 Jake's way of working is: changes go into that repository, it builds and verifies a release, and this site takes the newest one from it (see Publishing a release). Releases up to rc.9 were built in Jake's Codex workspace (`Documents/Codex/2026-10-23/minecraft-progressive-smithing`), where the friends' server still runs.

The page serves both players and self-hosters. Download separates Jake’s server-approved auto-update Prism ZIP from the latest published manual client; these versions can differ. Download sections use their card’s full inner width without nested padded cards. The server card links the latest release’s verified ZIP and checksums. Older release rows retain their immutable client URLs, dates and in-page changelogs.

The overlay scrolls as one page, with three columns on desktop, two on tablets and one on phones. Playing introduces the survival loop and personal Armor/Tools tracks; credits span the full width beneath the guides.

## First-time install and updates

`player-guide.tsx` combines first-time setup, everyday auto-updates and manual migration. The old “Updating or switching installs” link was verified in the browser: it focused the already-visible After setup heading on desktop, producing little visible change. Its replacement is a real button with `aria-controls` and `aria-expanded`; it opens the update/migration disclosure, scrolls its heading into view and moves keyboard focus there without adding a browser-history entry. The native summary can also open or close it.

First-time setup explains Minecraft Java ownership, Microsoft sign-in, and “instance” as a separate Minecraft setup. Players download the automatic ZIP, **keep it zipped without running its contents**, use Prism **Add Instance → Import**, name/confirm the setup, review only the expected bundled Packwiz/HTTPS website command, and launch to fetch required files with Java 21 and about 4 GB memory if asked. They then add the host-supplied address; downloading the client grants neither an address nor server access. Manual clients and self-hosting have separate paths. A short troubleshooting disclosure covers accidentally opening the ZIP, failed update checks and missing address/access. After setup, close Minecraft and launch the same automatic setup in Prism while online; do not re-import every release. Failed checks block launch; game/loader upgrades can require a new starter. A manual `.mrpack` never becomes automatic by itself.

Migration keeps the old instance backed up using **Copy… → Select all**, imports separately, copies only personal options/server lists and optional worlds/resources/screenshots, and leaves mods, pack-owned configs, account files and updater state behind. Multiplayer progression remains on the server. Full instructions remain at `packwiz/Install-and-Update.md`; legacy guide/download URLs remain unchanged.

## Generated mod credits

`node scripts/generate-mod-credits.mjs` runs before every production build. Membership comes exclusively from **mods.lock.json inside the published server ZIP**, covering client, server-only and supporting mods. It reads the approved version from `packwiz/current.json` and the newest manual version from `releases.json`; when different, both manifests are represented. The server archive must match its published SHA-256 and the manifest must match the release version. Approve only versions whose server release is also in the public index. Unknown providers or missing author/license metadata fail the build instead of omitting a bundled mod.

`scripts/modpack-projects.json` caches official project attribution, not membership. Modrinth CDN project IDs resolve through the official project/team APIs. FTB Maven coordinates resolve through FTBTeam’s official repository manifest and license file (or the manifest’s declared license if no standalone license exists). The cached `evidence` links record those sources. Roles are preserved so project maintainers/builders are not mislabeled as sole authors. Project licenses and source links lead to the publishers; these credits do not replace upstream notices. A new pinned mod automatically joins the list, and a removed mod leaves it even when metadata remains cached. The generator also reads embedded author/license declarations from each exact pinned JAR, verified by SHA-256 and cached by artifact hash in `scripts/modpack-artifacts.json`. This preserves original credits such as shedaniel and Mozilla even when a current project-team listing differs. New pinned artifacts are fetched only to inspect metadata; no dependency is installed or upgraded. Unsupported metadata formats fail with an actionable error.

The generated `src/common/modpack-credits.json` is bundled in the hashed app assets, avoiding a mutable public credits pointer or a second release feed. `mod-credits.tsx` displays versions, side, original author declarations, project-team links, license and source in readable responsive rows. It only labels a snapshot as approved when it matches the runtime approved feed; a newer feed shows an explicit refresh message until the site is rebuilt. Run `yarn modpack:credits` to refresh after publication changes, review/cache any newly resolved metadata and commit the generated snapshot. To refresh existing project attribution, remove its cache entry and rerun; no manually curated membership list is required.

## Publishing a release

1. Build and verify the release in the pack repository (its README has the details). `python work/build-release.py --version <version>` writes `outputs/Progression-Survival-<version>/`, holding `mods.lock.json`, `Release-Notes.md`, one `.mrpack`, one `Progression-Survival-Server-*.zip` and the archives' hashes in `latest.json` (some older builds wrote `SHA256SUMS.txt`). `python work/verify-first-pack.py --version <version>` checks every download against its pinned hash and only then copies the release to `outputs/Latest-Release/`.
2. Take it into the site:
   ```bash
   yarn modpack:release
   ```
   With no folder named, the script reads the pack repository's `outputs/Latest-Release/`. It finds the repository beside this one's main checkout, so it works from a worktree too; `MODPACK_REPO` points it elsewhere. If that version is already published, it says "Up to date" and writes nothing. `--dry-run` runs every check and writes nothing. A folder can still be named, e.g. an older build left in the Codex workspace.
3. Commit it and merge it into `staging` (see CLAUDE.md's Branches and staging). The deploy uploads it when Jake next deploys.

`scripts/release-modpack.mjs` refuses a release whose archives don't match the builder's `SHA256SUMS.txt` (or, without one, the `artifacts` in its `latest.json`), or that contain worlds, player data, admin lists, `server.properties` or logs. Since 2026-10-29 it also refuses a player's own client files: `options.txt` (and `optionsof.txt`, `optionsshaders.txt`), `servers.dat`, `saves/`, `screenshots/` and a launcher's `accounts.json`. A pack shipping the builder's `options.txt` would replace every player's settings on import. A mod config that happens to be called `options.txt` would trip it too; rename it in the builder rather than loosening the check. Since 2026-10-30 it also refuses KubeJS's `kubejs/config/web_server.json`, which holds the builder's private access token for KubeJS's local web server (Jake chose this knowing it makes rc.9 unpublishable). KubeJS writes its own when a server starts, and the pack repository's builder leaves it out. It copies the two archives and the notes into `public/downloads/progression-survival/releases/<version>/`, writes a checksum file covering just those two archives, and regenerates:
- **`releases.json`:** every release, newest first. The download page and the board's modpack tile read it at runtime (`src/common/modpack.ts`), so a release needs no code change.
- **`latest.json`:** the newest release on its own.
- **`.htaccess`:** `latest.mrpack` and `latest-server.zip` answer with a 302 to the newest files, never a 301, which browsers would remember forever. It also sets `no-cache` on the JSON files and `no-store` on those redirects.

The deploy uploads `releases.json`, `latest.json`, `.htaccess` and `Install-and-Update.md` on every run (see the workflow). They can change between versions without changing length, and the deploy otherwise compares files by size.

## Rules

- **A deployed release folder is never edited, overwritten or deleted.** Friends and the `latest` redirects may point at it, and the deploy wouldn't notice a same-size change anyway. A fix goes out as a new version. `--force` is only for a version that hasn't been pushed yet.
- **Only four files per release are published:** the client `.mrpack`, the server `.zip`, `Release-Notes.md`, and a `SHA256SUMS.txt` covering the two archives. The builder's other output stays in its workspace on purpose. That includes the custom-source ZIP (it holds local paths and test-command names), `mods.lock.json`, `package-acceptance.json` and the other verification files.
- **Third-party mod jars are never hosted here.** The `.mrpack` downloads them from their publishers (Modrinth, FTB's Maven), because the mods' licences haven't been checked for redistribution.
- **`releases.json`, `latest.json` and the folder's `.htaccess` are generated.** Edit the script, not the output.
